# SDK M0 — Secure Contract Foundation

**Status:** implemented on the hardened v0.1 line  
**SDK:** 0.1.x  
**Platform API:** 1.1  
**Scope:** transport security, response integrity, bounded resource use, and executable contract conformance

## M0 objective

M0 establishes a fail-closed external SDK boundary around the existing Platform API 1.1 operation gateway. It does not expand the remote API.

The SDK must be the official developer-facing contract client, not an authority engine. R10 remains authoritative in the Platform repository.

## Completed M0 controls

- HTTPS is required by default.
- Plain HTTP requires explicit \`allow_insecure_http=True\` and is intended only for controlled local/test environments.
- Base URLs reject userinfo, query strings, and fragments.
- Automatic redirects are disabled for authenticated requests.
- Response \`X-Tinlance-API-Version\` must exactly match \`1.1\`.
- Response \`Content-Type\` must be \`application/json\` (parameters such as \`charset=utf-8\` are accepted).
- Response bodies are bounded by a configurable limit; default is 8 MiB.
- Declared and actual response sizes are checked.
- Error responses receive the same content-type/version checks and size bound.
- Success status is validated per operation: read operations require \`ok\`; consequential operations require \`accepted\`.
- Consequential operations continue to use the caller request ID as their idempotency key.
- No automatic retry is introduced for consequential operations.
- The public operation surface remains exactly the twelve Platform 1.1 operations, including R10 governed execution.
- Unsupported capabilities remain deferred until the Platform publishes versioned contracts.

## Security rationale

The SDK carries bearer credentials, so transport confidentiality and origin integrity are part of the SDK boundary. OWASP recommends TLS for authenticated web-service communication, and RFC 9110 treats HTTPS and HTTP as distinct origins and calls for care around authorization credentials during redirects.

The SDK therefore fails closed rather than attempting to make an insecure or redirected authenticated request succeed.

## M0 acceptance gates

1. Unit and real-HTTP contract tests cover the public operation surface, including R10.
2. Response API-version mismatch is rejected.
3. Invalid response media type is rejected.
4. Oversized responses are rejected, including bounded reads without relying solely on \`Content-Length\`.
5. Redirects do not become authenticated follow-on requests.
6. HTTP is rejected by default.
7. Operation-specific success envelopes are enforced.
8. Existing request-size, request-ID, W3C trace-context, idempotency, typing, lint, coverage, dependency-audit, and SBOM gates remain green.
9. The SDK imports no Platform implementation package.
10. No client-side authorization, policy, approval, tool, secret, sandbox, evidence, or execution authority is introduced.

## Explicit non-goals

M0 does not invent:

- approval decision endpoints;
- direct tool execution;
- streaming;
- pagination;
- webhooks;
- resource-oriented REST paths;
- generated OpenAPI clients;
- client-side policy enforcement;
- durable distributed idempotency.

Those require corresponding Platform contracts first.
